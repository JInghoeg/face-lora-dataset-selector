# v0.3 Execution Plan

Status: ACTIVE PLANNING
Tracking issue: #2
Research background: docs/V0.3_RESEARCH_GUIDED_PLAN.md

## Goal

v0.3 must improve the actual job of this project:

> select and compose a better person/character LoRA training set.

Image quality, face detection, pose, similarity, and UI are supporting signals and workflows. They are not the product goal by themselves.

## Current project state

- The Valby dataset is still being collected.
- The current Valby pool has not yet been screened with v0.2.
- Therefore v0.3 must not require an artificial benchmark before development can begin.
- The first real benchmark will be derived later from one frozen Valby snapshot and real v0.2/v0.3 disagreements.
- Only one practical dataset is required for the first validation cycle. Do not require three separate subject datasets.

## Frozen decisions

1. Human review remains authoritative.
2. Top N / Bottom N is required and will be improved, not removed.
3. Low face ratio alone must never be a hard reject.
4. "Multiple face detections" is not equivalent to "multiple people".
5. Per-image quality and dataset-level contribution are separate concepts.
6. Do not freeze a new opaque composite score before real LoRA-oriented validation.
7. Model quality comes before package size.
8. If a default model is needed and redistribution is permitted, bundle it.
9. FiftyOne is a workflow reference only; do not turn this project into a generic dataset manager.
10. Do not expand v0.3 into captioning, training management, scraping, or generic annotation.

## Release scope

### Must ship

- separate analysis metrics, review flags, and hard rejects;
- PASS / REVIEW / REJECT eligibility state;
- primary-face handling;
- store and display face boxes and confidence;
- safe cache/schema migration;
- dedicated duplicate-group human review;
- predictable filter/sort/view behavior;
- improved Top N / Bottom N on the current filtered view.

### Ship only if validated in time

- dataset-level coverage/redundancy recommendation;
- semantic visual similarity / uniqueness;
- stronger replacement or auxiliary models;
- attribute-binding / disentanglement scoring.

### Deferred

- caption generation;
- LoRA training orchestration;
- dataset scraping/acquisition;
- generic CV annotation;
- destructive auto-deletion.

## Phase 0 — Research guardrails

Can start immediately.

Deliverables:

- map personalization/LoRA research claims to selector requirements;
- define which observations may hard-reject and which may only warn/rank;
- define the later v0.2 vs v0.3 comparison protocol;
- define a minimal benchmark record schema.

Gate:

- no new dataset-level composite recommendation formula becomes default before real Valby evidence exists.

## Phase 1 — Core correctness

Priority: P0.
Can be implemented before Valby collection is finished.

Deliverables:

- split analysis_metrics / review_flags / hard_rejects;
- remove low-face-ratio-only rejection;
- continue primary-face analysis when secondary detections exist;
- persist every face detection with bbox and confidence;
- choose/store a primary face;
- expose face boxes in UI for inspection;
- preserve manual override precedence;
- migrate old cache safely or force a clean re-analysis when migration is unsafe.

Acceptance:

- useful high-resolution small-face samples are not rejected only for ratio;
- false extra-face detections do not automatically reject the sample;
- primary-face metrics still run when extra detections exist;
- user can see what the detector actually detected.

## Phase 2 — Human review workflow

Priority: P1.
Can proceed while collection is still ongoing.

### Duplicate group review

Required workflow:

- review one duplicate group at a time;
- compare members side by side;
- show the few metrics that help selection;
- highlight the algorithm's proposed best member;
- allow keep best / keep selected / keep all / mark not duplicate / split group;
- never silently delete ambiguous members.

### View / Filter / Sort

Mental model:

Dataset
-> scope
-> filters
-> sort
-> optional Top/Bottom N
-> human action

Rules:

- filtering changes membership;
- sorting changes order only;
- Top/Bottom limits the current filtered view;
- changing Top/Bottom must not silently clear filters;
- current scope, filters, sort basis, and Top/Bottom state must be visible.

### Top N / Bottom N

Keep as a first-class QA tool.

Controls:

- Top / Bottom;
- N = 10 / 25 / 50 / custom;
- ranking basis.

This is used both for selection and for checking whether a metric/ranking behaves sensibly.

## Phase 3 — Freeze one Valby snapshot

Wait until collection reaches a natural stopping point.

Process:

1. copy/freeze one raw Valby snapshot;
2. do not destructively edit it;
3. run v0.2 on the snapshot;
4. run the current v0.3 candidate on the same snapshot;
5. inspect disagreements;
6. convert confirmed real failures into Benchmark v1.

Benchmark v1 should grow from real errors such as:

- high-resolution useful small-face images;
- false extra-face detections;
- true multi-person images;
- near-duplicate groups;
- similar-but-useful variants;
- redundant high-quality variants;
- coverage-critical weaker-quality samples;
- pose/view/outfit correlations.

Do not manufacture a quota merely to make the benchmark look complete.

## Phase 4 — Dataset-level recommendation

Only after Phase 3 provides real evidence.

Candidate dimensions:

- Identity Evidence;
- Coverage Value;
- Disentanglement Value;
- Redundancy Cost;
- Technical / Perceptual Quality.

Important:

- the same image may have different recommendation value in different datasets;
- dataset contribution must be explainable;
- no opaque "AI score" should directly decide rejection;
- exact weights and formulas are not frozen in advance.

Gate:

- before becoming default, a major recommendation change must show useful improvement on the frozen Valby comparison and later LoRA output validation.

## Phase 5 — Model upgrades

Evaluate models only after the selector failure mode is defined.

Selection priority:

1. measurable benefit to LoRA dataset selection;
2. robustness on the actual data;
3. domain relevance;
4. redistribution/license compatibility;
5. engineering stability;
6. runtime;
7. package size.

Do not replace a model merely because another model is stronger on an unrelated benchmark.

## Validation strategy

### Before Valby snapshot exists

Regression-test known logic:

- hard reject vs review flag behavior;
- primary-face selection;
- extra-face handling;
- duplicate-group actions;
- view/filter/sort/Top-Bottom state.

### After Valby snapshot exists

Compare v0.2 and v0.3 on exactly the same images.

Primary review questions:

- What did v0.2 wrongly reject?
- What did v0.3 newly send to REVIEW?
- Did primary-face handling improve?
- Are duplicate groups easier and safer to resolve?
- Are Top/Bottom results understandable?
- Does the selected set have better useful coverage with less redundant evidence?

### LoRA outcome validation

Required before dataset-level recommendation math is considered stable.

For the first cycle, two training subsets are enough:

- v0.2-selected subset;
- v0.3-selected subset.

Keep training settings fixed.

Evaluate:

- identity fidelity;
- novel pose/view generalization;
- prompt adherence;
- environment/background generalization;
- body/face consistency;
- overfitting / training-image reproduction;
- diversity.

A third training run is not mandatory unless a later question actually needs it.

## Development cost / risk

- Core correctness: medium effort, medium-high regression risk.
- Duplicate review UI: medium effort.
- View/filter/sort redesign: medium-high UI regression risk.
- Top/Bottom redesign: low-medium effort.
- Dataset-level recommendation: high research risk.
- New model integration: variable; only justified by measured value.

Overall v0.3 remains a medium-high project, but the work is staged so that useful correctness fixes land before the research-heavy recommendation system.

## Definition of done

v0.3 is not done until:

- low face ratio alone no longer rejects a useful image;
- false extra face detections no longer auto-reject;
- face boxes/confidence can be inspected;
- duplicate groups have a practical human QA workflow;
- filters/sorts behave predictably;
- Top N / Bottom N works clearly on the current view;
- manual decisions remain authoritative;
- default recommendation does not rely on an unvalidated opaque score;
- required redistributable models are bundled;
- quality is not sacrificed merely to reduce package size.
