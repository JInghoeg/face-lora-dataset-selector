# v0.3 Execution Plan

Status: ACTIVE PLANNING
Tracking issue: #2
Research background: docs/V0.3_RESEARCH_GUIDED_PLAN.md

## Product goal

v0.3 is not only a bug-fix release.

Its main job is to turn Face LoRA Dataset Selector into a better **working environment for selecting, reviewing, understanding, and synchronizing a person/character LoRA dataset**.

The release has three equal mainlines:

1. **Correctness** — stop false rejects / false multi-face decisions and make scoring evidence inspectable.
2. **Dataset workflow** — learn from mature FiftyOne concepts without cloning FiftyOne.
3. **AI synchronization** — let the user export the current local dataset state in a compact, reviewable form so ChatGPT can understand the actual collected dataset and return structured review suggestions.

The final optimization target remains LoRA training-set quality.

## Current project state

- The Valby dataset is still being collected.
- It has not yet been screened with v0.2.
- Do not interrupt collection to manufacture a benchmark.
- The first real benchmark will be derived later from one frozen Valby snapshot and actual v0.2/v0.3 disagreements.
- One Valby dataset is enough for the first validation cycle.

## Frozen decisions

1. Human review is authoritative.
2. Top N / Bottom N remains and is improved, not removed.
3. Low face ratio alone can never hard-reject a useful image.
4. Multiple face detections do not automatically mean multiple people.
5. Per-image quality and dataset-level contribution are separate.
6. No opaque composite score becomes default before LoRA-oriented validation.
7. Model quality comes before package size.
8. Required default models are bundled when redistribution permits.
9. FiftyOne is a workflow reference, not a replacement architecture.
10. Dataset synchronization with ChatGPT is a v0.3 mainline requirement, not a future extra.
11. AI synchronization is bidirectional: export review bundles and import `review_patch.json` into a separate AI suggestion layer.
12. AI suggestions never silently overwrite manual decisions; the user explicitly accepts/rejects them.
13. Do not expand v0.3 into caption generation, LoRA training management, scraping, or generic CV annotation.

## What to learn from FiftyOne

The useful ideas are architectural/workflow ideas:

### 1. Dataset vs View

Keep one persistent dataset state. Filtering, sorting, similarity search, Top/Bottom, and other browsing operations create a **View** over that state rather than mutating the dataset.

Required consequences:

- filters change membership;
- sorting changes order;
- Top/Bottom limits the current view;
- leaving Top/Bottom restores the same view;
- current view state is visible;
- useful views can be saved and reloaded.

### 2. Sample-level vs detection-level data

Do not collapse detector results into one integer like `faces=2`.

A sample should retain its own fields, while face detections are child records with:

- bbox;
- detector confidence;
- pixel size;
- area ratio;
- primary/secondary role;
- optional review state.

This enables visual QA and prevents a weak secondary detection from destroying a valid sample.

### 3. Field-driven filtering

Analysis fields should be first-class typed fields that can be filtered/sorted without hard-coding every future workflow into one giant combo box.

Examples:

- eligibility;
- manual status;
- yaw;
- pitch;
- shot size;
- face quality;
- face effective pixels;
- duplicate group;
- source;
- future outfit / hairstyle / semantic similarity fields.

### 4. Saved views

Useful review states should be savable as rules, for example:

- `右3/4 + 全身 + REVIEW`;
- `当前 Bottom 10 by Identity Evidence`;
- `有可疑第二张脸`;
- `Duplicate Group 未审核`.

Saved views store the query/review recipe, not copied images.

### 5. Similarity review

Keep two concepts separate:

- near duplicate: pHash / burst-frame style;
- visual/semantic similarity: embedding-based.

Similarity is a review/navigation tool, not an automatic delete command.

Later, if validated, support both:

- whole-image similarity;
- face-patch similarity.

### 6. Export the current View

Any current filtered/sorted view should be exportable as a portable review package. This is the key bridge to ChatGPT synchronization.

## v0.3 release scope

### Must ship

#### Correctness
- analysis_metrics / review_flags / hard_rejects separation;
- PASS / REVIEW / REJECT eligibility;
- primary-face handling;
- face detections persisted with bbox + confidence;
- face-box visual QA;
- safe cache/schema migration.

#### Human review
- dedicated duplicate-group review;
- predictable Dataset/View/Filter/Sort behavior;
- saved views;
- improved Top N / Bottom N on the current view.

#### AI synchronization
- stable sample IDs;
- export current dataset or current view as an AI review bundle;
- manifest containing selector state and analysis fields;
- summary of dataset composition;
- contact sheets with visible sample IDs;
- optional export of selected/full-resolution originals for close inspection;
- enough metadata to reconnect any AI comment to the exact local sample.

### Ship if validated in time

- semantic visual similarity / uniqueness;
- face-patch similarity;
- dataset-level coverage/redundancy recommendation;
- outfit/background correlation analysis;
- stronger replacement/auxiliary models.

### Deferred

- automatic caption generation;
- LoRA training orchestration;
- dataset scraping/acquisition;
- generic CV annotation;
- destructive automatic deletion.

## AI Sync Bridge

This is a first-class v0.3 feature.

### Goal

The user should not have to describe a large local dataset from memory.

The selector should generate a portable snapshot that ChatGPT can inspect to answer questions such as:

- What is this dataset currently missing?
- Which groups are redundant?
- Which images deserve full-resolution inspection?
- Is angle / shot-size / outfit distribution biased?
- Which images look suspicious despite high automatic scores?
- Which cases should be sent to REVIEW?

### Proposed export package

```
AI_Review_Bundle/
├─ manifest.csv
├─ manifest.json
├─ summary.json
├─ views.json
├─ contact_sheets/
│  ├─ all_001.jpg
│  ├─ current_view_001.jpg
│  └─ duplicate_groups/
└─ originals/              # optional: selected/current-view originals only
```

### Required manifest concepts

At minimum:

- stable sample_id;
- relative filename/path;
- width / height;
- source;
- automatic status;
- manual status;
- eligibility;
- review flags;
- hard rejects;
- face detections;
- primary-face metrics;
- yaw / pitch / roll;
- shot size;
- duplicate group;
- existing quality metrics.

Future fields can be added without breaking old bundles.

### Contact sheets

Contact sheets are not decorative. They are the visual index that lets ChatGPT and the user refer to exact samples.

Requirements:

- every tile visibly contains sample_id and short filename;
- layout preserves enough image area for visual review;
- generate multiple pages rather than unreadably tiny tiles;
- allow contact sheets for the whole dataset, current view, and duplicate groups.

### Round-trip review — confirmed

Recommended design:

ChatGPT can return a `review_patch.json` keyed by `sample_id`.

Importing it should create a separate **AI suggestion layer**, for example:

- suggested eligibility/status;
- suggested flags;
- note;
- requested full-resolution review.

It must **not overwrite the user's manual decision automatically**.

The user can accept/reject AI suggestions in the app.

Round-trip import is a frozen v0.3 requirement. AI output must remain a separate suggestion layer and must never silently overwrite manual decisions.

## Phase 0 — Research and data-model guardrails

Can start immediately.

Deliverables:

- define hard-reject vs review-only evidence;
- define stable sample/detection schema;
- define View representation;
- define AI Review Bundle schema;
- define later v0.2 vs v0.3 comparison protocol.

Gate:

- no new dataset-level composite recommendation formula before real Valby evidence exists.

## Phase 1 — Core correctness + data model

Priority: P0.

Deliverables:

- metrics / flags / hard rejects split;
- PASS / REVIEW / REJECT;
- primary-face logic;
- persist all face detections;
- face-box QA;
- stable sample IDs;
- safe cache migration.

Acceptance:

- low face ratio alone does not reject;
- false extra-face detection does not auto-reject;
- primary-face metrics still run when extra detections exist;
- exact detector boxes can be inspected;
- sample IDs survive normal app restarts and are exported consistently.

## Phase 2 — Dataset/View workflow

Priority: P1.

Deliverables:

- explicit Dataset -> View model;
- field-driven filters;
- independent sorting;
- saved views;
- visible current-view state;
- Top N / Bottom N with N and ranking basis;
- state regression tests.

## Phase 3 — Duplicate / similarity human review

Priority: P1.

Deliverables:

- dedicated duplicate-group review;
- side-by-side group members;
- proposed best member;
- keep best / keep selected / keep all / mark not duplicate / split group;
- preserve human decisions.

If semantic similarity is ready and validated, it can use the same review surface without pretending similarity == duplicate.

## Phase 4 — AI synchronization

Priority: P1 and must ship.

Deliverables:

- export whole dataset or current view;
- manifest.csv + manifest.json;
- summary.json;
- contact sheets;
- optional selected originals;
- bundle version/schema metadata;
- import `review_patch.json` keyed by stable `sample_id`;
- show AI suggestions separately from manual state;
- allow accept / reject / clear AI suggestion actions;
- never auto-apply AI status over a manual decision.

Add round-trip `review_patch.json` import as a separate AI suggestion layer.

Acceptance:

- the user can generate one bundle, upload it to ChatGPT, and ChatGPT can refer unambiguously to exact samples;
- no absolute local path is required for the AI side;
- exporting a view does not alter dataset state;
- re-export preserves stable sample IDs;
- imported AI suggestions map to the exact local sample;
- malformed, stale, unknown-ID, or schema-incompatible patches are rejected safely;
- AI suggestions remain reviewable and reversible.

## Phase 5 — Freeze one Valby snapshot and build Benchmark v1

Wait for a natural collection stop.

Process:

1. freeze one raw Valby snapshot;
2. run v0.2;
3. run the current v0.3 candidate;
4. inspect disagreements;
5. collect confirmed real failures into Benchmark v1;
6. use the AI Sync Bridge itself during this audit.

Do not manufacture a quota.

## Phase 6 — Dataset-level recommendation

Only after real evidence exists.

Candidate dimensions:

- Identity Evidence;
- Coverage Value;
- Disentanglement Value;
- Redundancy Cost;
- Technical / Perceptual Quality.

The same image may have different value in different datasets.

No exact formula is frozen in advance.

## Phase 7 — Model upgrades

Evaluate only against confirmed selector failure modes.

Priority:

1. benefit to LoRA dataset selection;
2. robustness on actual data;
3. domain relevance;
4. redistribution/license compatibility;
5. engineering stability;
6. runtime;
7. package size.

Required redistributable default models are bundled.

## Validation

Before the frozen Valby snapshot exists, regression-test:

- reject vs review behavior;
- primary face;
- extra-face handling;
- duplicate review actions;
- View/filter/sort/Top-Bottom state;
- saved views;
- AI bundle stability and sample ID mapping.

After the snapshot exists, compare v0.2 and v0.3 on the same images.

Later LoRA validation can use two subsets:

- v0.2-selected;
- v0.3-selected.

A third training run is not mandatory.

## Definition of done

v0.3 is not done until:

- low face ratio alone no longer false-rejects;
- false extra-face detections no longer auto-reject;
- face detections are inspectable;
- duplicate groups have practical human QA;
- Dataset/View/Filter/Sort is understandable;
- Top N / Bottom N behaves predictably;
- useful Views can be saved;
- an AI Review Bundle can synchronize the actual local dataset with ChatGPT;
- stable IDs let AI review map back to exact local samples;
- `review_patch.json` can round-trip AI suggestions back into the app without modifying manual decisions;
- manual decisions remain authoritative;
- no unvalidated opaque score controls selection;
- required redistributable models are bundled;
- quality is not sacrificed merely to reduce package size.
