# v0.3 Phase 1 — Data Model and Migration Design

Status: REVIEWED DESIGN CANDIDATE
Parent plan: docs/V0.3_EXECUTION_PLAN.md
Tracking issue: #2

## 1. Why the v0.2 data model must change

Current v0.2 behavior in `app.py` has three structural problems:

1. `Photo.reasons` mixes detector observations, quality warnings, and fatal failures.
2. `Analyzer.base()` maps any non-empty `reasons` list directly to `auto_status='淘汰'`.
3. Primary-face analysis only runs when `faces == 1`.

As a result:

- low face ratio can become a hard reject even when the face has enough absolute pixels;
- one false secondary YuNet detection can prevent FIQA / head-pose / face-sharpness analysis of the real subject;
- the UI cannot show what the detector actually saw;
- AI export has no machine-readable distinction between facts, warnings, and decisions.

v0.3 must fix the data model before changing recommendation math.

---

## 2. Design principles

1. **Measurements are facts; flags are interpretations; decisions are decisions.**
2. A detector output must be persisted before it is collapsed into sample-level state.
3. Manual decisions and AI suggestions are separate layers.
4. AI suggestions never overwrite manual decisions automatically.
5. Dataset/View state is separate from sample state.
6. Stable sample identity must survive normal restarts and file renames/moves when image content is unchanged.
7. Do not freeze new model thresholds in this schema document.

---

## 3. Stable sample identity

### 3.1 Content hash

Each image gets a full SHA-256 content hash:

```python
content_sha256: str
```

Compute it only for new or changed files and cache it.

### 3.2 sample_id

Human/AI-facing stable ID:

```text
img_<first 16 hex chars of content_sha256>
```

Example:

```text
img_7f2a91d43b2ce801
```

Properties:

- unchanged image keeps the same ID after rename or moving within the dataset;
- edited image becomes a new sample;
- full SHA-256 remains stored for collision verification;
- UI may display the short `sample_id`; export keeps both fields.

Do not derive AI-facing IDs from absolute Windows paths.

---

## 4. Detection-level data

Introduce a child record rather than storing only `faces:int`.

### FaceDetection

```python
@dataclass
class FaceDetection:
    detection_id: str
    bbox_xywh: tuple[float, float, float, float]   # image pixel coordinates
    confidence: float
    area_ratio: float
    face_px: int
    is_primary: bool = False
    detector: str = "yunet"
```

Possible later fields are additive:

- face quality for each detection;
- embedding;
- landmarks;
- detector-consensus metadata.

Do not require them for Phase 1.

### Derived compatibility values

```python
faces = len(face_detections)
primary_face = next((x for x in face_detections if x.is_primary), None)
```

The existing `faces`, `face_ratio`, and `face_px` UI can temporarily be derived from this structure to reduce regression risk.

---

## 5. Primary-face handling

Phase 1 must always attempt to choose a primary-face candidate when at least one detection exists.

The schema freezes **the behavior**, not a new threshold formula:

1. persist all detections first;
2. deterministically select one primary candidate;
3. run primary-face FIQA / face sharpness / head-pose analysis even if secondary detections exist;
4. retain secondary detections for QA;
5. sample-level multi-person interpretation is a separate flag/decision step.

The exact heuristic for declaring a secondary detection a probable second person remains configurable and must be validated on real Valby cases.

A tiny/weak secondary face box must not erase the main subject's measurements.

---

## 6. Structured analysis findings

Replace the semantic role of free-text `reasons`.

### AnalysisFinding

```python
@dataclass
class AnalysisFinding:
    code: str
    source: str
    value: Optional[float] = None
    threshold: Optional[float] = None
    detail: Optional[str] = None
```

UI text should be generated from `code`, so exports remain machine-readable.

Examples of codes:

```text
read_error
no_face_detected
secondary_faces_detected
probable_multi_person
low_resolution
low_face_pixels
low_face_ratio
severe_face_blur
low_face_quality
high_brisque
extreme_exposure
```

### Three separate containers

```python
analysis_metrics: dict[str, Any]
review_flags: list[AnalysisFinding]
hard_rejects: list[AnalysisFinding]
```

Important:

- `low_face_ratio` is review/ranking evidence, not a hard reject by itself;
- `secondary_faces_detected` is an observation/review flag, not a hard reject by itself;
- hard reject policy is intentionally conservative.

---

## 7. Eligibility vs selection recommendation

Do not use one field for both.

### Eligibility

```text
PASS
REVIEW
REJECT
```

Meaning:

- PASS — no confirmed fatal issue;
- REVIEW — human inspection is warranted;
- REJECT — high-confidence fatal/unusable problem.

Eligibility is derived from hard rejects + review flags.

### Selection state

Keep the existing user-facing selection vocabulary during v0.3 migration:

```text
推荐
备选
淘汰
```

Fields:

```python
auto_status: str
manual_status: Optional[str]
```

Rules:

- manual status has highest authority;
- an eligibility REJECT may force auto `淘汰`;
- a REVIEW does not automatically mean `淘汰`;
- redundancy or low marginal value should normally produce `备选`, not pretend the image is technically invalid.

The current `status = manual_status or auto_status` compatibility behavior may remain for UI display, but recommendation code must also inspect eligibility explicitly.

## 8. Proposed Photo v3 shape

Conceptual structure:

```python
@dataclass
class Photo:
    path: Path

    # identity / file state
    sample_id: str = ""
    content_sha256: str = ""
    file_size: int = 0
    mtime_ns: int = 0
    width: int = 0
    height: int = 0

    # detector-level evidence
    face_detections: list[FaceDetection] = field(default_factory=list)
    primary_face_id: Optional[str] = None

    # current primary-face/image metrics
    face_ratio: float = 0.0
    face_px: int = 0
    blur: float = 0.0
    brightness: float = 0.0
    face_quality: float = 0.0
    brisque: float = 0.0
    yaw: float = 0.0
    pitch: float = 0.0
    roll: float = 0.0
    angle_class: str = "未检测"
    pitch_class: str = "未检测"
    person_scale: str = "未检测身体"
    phash: int = 0
    duplicate_group: int = 0

    # interpretation
    analysis_metrics: dict = field(default_factory=dict)
    review_flags: list[AnalysisFinding] = field(default_factory=list)
    hard_rejects: list[AnalysisFinding] = field(default_factory=list)
    eligibility: str = "REVIEW"

    # selection
    auto_status: str = "备选"
    manual_status: Optional[str] = None

    # AI suggestion layer
    ai_suggestion: Optional[AISuggestion] = None
```

This is conceptual schema, not an instruction to rewrite the entire application into many modules in one commit.

## 9. AI suggestion layer

Confirmed v0.3 requirement.

### AISuggestion

```python
@dataclass
class AISuggestion:
    patch_id: str
    bundle_id: str
    suggested_eligibility: Optional[str] = None
    suggested_status: Optional[str] = None
    flags: list[str] = field(default_factory=list)
    note: str = ""
    request_full_resolution: bool = False
```

Rules:

- stored separately from `manual_status`;
- visible in UI as AI suggestion;
- user can Accept / Reject / Clear;
- import never silently mutates manual status;
- accepting a suggestion is an explicit human action and should be auditable.

---

## 10. review_patch.json contract

Top level:

```json
{
  "schema_version": 1,
  "bundle_id": "...",
  "suggestions": [
    {
      "sample_id": "img_7f2a91d43b2ce801",
      "suggested_eligibility": "REVIEW",
      "suggested_status": "备选",
      "flags": ["possible_redundancy"],
      "note": "Compare with img_...",
      "request_full_resolution": true
    }
  ]
}
```

Importer checks:

- schema version supported;
- sample_id exists;
- full content hash still matches the local sample when supplied;
- duplicate sample IDs in one patch are rejected;
- unknown IDs are reported, not guessed;
- stale bundle metadata produces a warning;
- malformed records do not partially overwrite manual data.

## 11. Dataset / View state

Do not persist filters by mutating Photo fields.

### ViewSpec

```python
@dataclass
class ViewSpec:
    view_id: str
    name: str
    filters: list[FilterSpec]
    sort_field: Optional[str]
    sort_direction: str = "desc"
    limit_mode: Optional[str] = None   # top / bottom
    limit_n: Optional[int] = None
    ranking_basis: Optional[str] = None
```

### FilterSpec

```python
@dataclass
class FilterSpec:
    field: str
    operator: str
    value: Any
```

Examples:

```text
eligibility == REVIEW
angle_class == 右3/4
person_scale == 全身
review_flags contains secondary_faces_detected
duplicate_group > 0
```

Saved Views persist ViewSpec only.

## 12. Cache v3 migration

Current cache version is 2.

v0.3 should introduce version 3.

### Safe migration policy

Do not blindly convert old `reasons` into new hard rejects.

Why:

- v2 `reasons` mixed warnings and fatal conditions;
- carrying them forward would preserve the exact bug v0.3 is fixing;
- v2 does not contain face detection boxes/confidence.

### Migration behavior

When opening a v2 cache:

1. preserve `manual_status`;
2. preserve only file metadata needed to detect unchanged files;
3. create/compute stable content hash + sample_id;
4. re-run the Phase 1 image analysis to populate detections/findings;
5. recompute eligibility and auto recommendation under v3 semantics;
6. save as cache version 3.

User manual decisions survive; obsolete automatic judgments do not.

If an image no longer exists or content changed, normal new/changed-file behavior applies.

---

## 13. Compatibility strategy

Avoid a giant one-shot refactor.

Recommended implementation order:

1. add new dataclasses/fields while keeping old UI fields;
2. implement v3 cache read/write and manual-state preservation;
3. persist all face detections;
4. choose primary face and run existing primary metrics for `faces >= 1`;
5. replace `reasons` generation with flags/hard rejects;
6. derive eligibility;
7. adapt old UI status display;
8. only then refactor View/filter/sort;
9. add AI bundle/patch on top of stable IDs.

This minimizes the chance of breaking the currently working scanner while changing its semantics.

## 14. Phase 1 acceptance tests

Minimum regression cases:

### A. High-resolution small-face

Expected:

- primary face analyzed;
- `low_face_ratio` may appear as REVIEW flag;
- no hard reject solely from ratio.

### B. Valid main face + tiny false secondary detection

Expected:

- all boxes persisted;
- correct primary face chosen;
- FIQA/yaw/sharpness still computed;
- sample not auto-rejected merely because detections > 1.

### C. Genuine multi-person image

Expected:

- multiple boxes visible;
- sample can reach REVIEW or REJECT only through explicit multi-person policy;
- user can inspect evidence.

### D. Read/corrupt failure

Expected:

- hard reject with machine-readable code;
- UI shows readable reason.

### E. v2 cache migration

Expected:

- manual statuses preserved;
- obsolete v2 automatic reasons not trusted;
- v3 analysis repopulates evidence.

### F. Rename unchanged image

Expected:

- same content SHA-256;
- same sample_id;
- AI references still resolve.

### G. Edit/replace image at same filename

Expected:

- new content SHA-256;
- new sample_id;
- stale AI patch cannot silently attach to the new content.

## 15. Review verdict

**PASS FOR IMPLEMENTATION DESIGN**

This schema addresses the confirmed v0.2 failure modes and supports the two other v0.3 mainlines:

- FiftyOne-style Dataset/View workflow;
- bidirectional AI dataset synchronization.

What is intentionally **not frozen** here:

- exact multi-person thresholds;
- new recommendation weights;
- new quality-model thresholds;
- semantic embedding model choice;
- dataset-level LoRA contribution formula.

Those decisions require real Valby evidence.
