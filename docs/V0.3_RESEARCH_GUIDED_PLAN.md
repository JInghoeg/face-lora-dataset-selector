# v0.3 Research-Guided LoRA Dataset Selector Plan

Status: **REVIEWED — CONDITIONAL PASS**

Branch: `planning/v0.3-research-guided-selector`

## 1. Product goal

This project is not a generic image-quality browser and not a generic computer-vision dataset manager.

The primary goal of v0.3 is:

> **Select and compose a training set that improves person/character LoRA identity learning, generalization, prompt controllability, and dataset diversity while reducing redundancy, accidental attribute binding, and avoidable bad samples.**

All image-quality, face-detection, pose, similarity, and UI work is subordinate to that final training goal.

### Frozen product principles

1. **LoRA training outcome is the primary optimization target.**
2. Per-image quality is necessary but insufficient; selection must consider the dataset as a set.
3. Identity-relevant evidence must be separated conceptually from identity-irrelevant factors such as background, pose, clothing, hairstyle, lighting, and composition.
4. Human review remains authoritative.
5. No model is rejected merely because it is large. Model size/performance is a secondary engineering concern after quality.
6. If a model is part of the default pipeline and its license permits redistribution, package it by default.
7. Optional download is justified by licensing/distribution constraints or genuinely optional functionality, not by size alone.
8. `Top N / Bottom N` is a required workflow and must remain.
9. Do not turn the application into a generic FiftyOne clone. Borrow mature workflow ideas where useful, but preserve LoRA-specific behavior.
10. Do not expand into captioning/training orchestration in this release unless required by the selector evaluation itself.

## 2. Research basis

The redesign must begin from subject-personalization / LoRA / DreamBooth-style training literature, not from isolated detector benchmarks.

### Primary literature and evidence

#### DreamBooth
Official DreamBooth data uses multiple images of the same subject captured under different conditions, environments, and angles. The method's goal is to preserve the specific subject while enabling synthesis in novel scenes, poses, views, and lighting.

- Paper: https://arxiv.org/abs/2208.12242
- Official dataset: https://github.com/google/dreambooth

**Implication for selector:** dataset diversity and cross-condition identity evidence are first-class requirements, not cosmetic bonuses.

#### DisenBooth
DisenBooth identifies entanglement between identity-relevant subject information and identity-irrelevant information such as background and pose as a central failure mode in subject-driven personalization.

- Paper: https://arxiv.org/abs/2305.03374
- Project: https://disenbooth.github.io/

**Implication for selector:** repeated co-occurrence of identity with one pose/background/outfit can be harmful even when every individual image is high quality.

#### A Data Perspective on Enhanced Identity Preservation for Diffusion Personalization — WACV 2025
This work explicitly attacks personalization from a data-centric perspective and shows that data design can improve identity preservation and text alignment.

- Paper: https://openaccess.thecvf.com/content/WACV2025/html/He_A_Data_Perspective_on_Enhanced_Identity_Preservation_for_Diffusion_Personalization_WACV_2025_paper.html

**Implication for selector:** dataset composition should be evaluated directly rather than treating selection as a chain of independent image-quality filters.

### Secondary literature

Additional personalization, disentanglement, overfitting, FIQA, IQA, face detection, embeddings, and data-selection research may be used to choose implementations **after** the LoRA-specific objective and validation protocol are defined.

## 3. Current v0.2 problems confirmed by code review

### P0-1 — Soft signals are incorrectly promoted to hard rejection

Current behavior stores many heterogeneous problems in `reasons`, then treats any non-empty `reasons` list as automatic rejection.

Example:

- low face ratio can cause rejection even when absolute face resolution is high and useful;
- moderate image-quality warnings and actual corruption are not structurally separated.

**Required change:** split observations into at least:

- `hard_rejects`
- `review_flags`
- `analysis_metrics`

A low face ratio alone must not hard-reject a high-resolution image.

### P0-2 — Multi-face detection can destroy an otherwise valid sample

Current behavior effectively treats `faces != 1` as a sample-level failure and does not complete the same primary-face analysis path.

**Required change:**

- persist each face detection: bbox, detector confidence, pixel size, area ratio;
- determine a primary face;
- classify secondary detections separately;
- only flag/reject a true multi-person sample when evidence is strong;
- expose face detections visually for human inspection.

Do not equate “two detector boxes” with “two people”.

### P1-1 — Duplicate groups exist but lack a real human QA workflow

The project already computes `duplicate_group`, group rank, and best member information, but there is no dedicated group-review workflow.

**Required change:** add a dedicated duplicate/similarity review view with side-by-side group members and actions such as:

- keep best
- keep selected
- keep all
- mark not duplicate
- split selected from group

Automatic ranking should highlight a proposed representative but never silently decide ambiguous groups.

### P1-2 — Filtering, sorting, Top/Bottom, and “best in duplicate group” have mixed mental models

The current UI combines:

- status filter
- shot-size filter
- yaw filter
- pitch filter
- duplicate-best filter
- sort
- hidden quick Top/Bottom mode

This makes the current result set hard to reason about.

**Required change:** adopt a clear view pipeline:

```
Dataset
  -> scope
  -> filters
  -> sort
  -> Top/Bottom N (optional view limiter)
  -> manual selection / review
```

Filtering changes membership. Sorting changes order. Top/Bottom N limits the current filtered view.

## 4. Top N / Bottom N — required redesign, not removal

This feature is retained because it is valuable for:

- quickly reviewing the best samples under a specific current view;
- quickly reviewing suspected worst samples;
- validating whether a ranking metric behaves sensibly;
- tuning thresholds and model behavior through human inspection.

### Proposed behavior

Controls:

- `Top N`
- `Bottom N`
- `N = 10 / 25 / 50 / custom`
- ranking basis selector

Possible ranking bases:

- recommendation value
- identity evidence
- perceptual/technical quality
- face effective resolution
- sharpness
- BRISQUE
- novelty / uniqueness
- another supported analysis metric

Rules:

1. Always operate on the **current filtered view**.
2. UI must visibly state the active filters and ranking basis.
3. Top/Bottom must not silently clear filters.
4. Switching Top/Bottom off restores the same filtered view.
5. It must remain useful even if the final recommender becomes dataset-aware.

## 5. v0.3 scoring architecture

Do **not** implement one opaque “quality score” that directly decides rejection.

The selector should separate four layers.

### Layer A — Per-image evidence

Measured facts, for example:

- image dimensions
- face detections
- primary-face effective pixel size
- face quality / identity utility
- technical/perceptual quality
- yaw / pitch / roll
- shot size / body visibility
- pHash
- visual embedding
- optional subject/background or attribute representations

### Layer B — Reliability flags

Examples:

- face is small in frame
- primary face has low effective resolution
- possible false secondary face
- probable multi-person image
- severe blur
- exposure issue
- exact/near duplicate
- unusual detector disagreement

These are inspectable observations, not automatically equivalent to rejection.

### Layer C — Eligibility

A conservative triage state:

- `PASS`
- `REVIEW`
- `REJECT`

Only high-confidence fatal problems should produce `REJECT`.

### Layer D — Dataset contribution / recommendation

A sample's value must depend on the current dataset, not only on itself.

Conceptually consider:

- **Identity Evidence** — does this image provide reliable subject identity?
- **Coverage Value** — does it fill a missing pose/view/shot/body condition?
- **Disentanglement Value** — does it help separate identity from outfit/background/pose/etc.?
- **Redundancy Cost** — is equivalent evidence already overrepresented?
- **Technical Quality** — is the usable signal degraded?

No final formula is frozen in this planning document.

A candidate formula or selection algorithm must first be validated against the LoRA-specific benchmark described below.

## 6. Research-first validation protocol — mandatory before freezing new scoring logic

This is the most important gate in v0.3.

### 6.1 Build a private evaluation corpus

Use at least three materially different subject-dataset types, for example:

- real-person photographic data;
- realistic game/CG character screenshots;
- mixed-source character/person data.

Do not commit private training images to this public repository.

The evaluation corpus should deliberately contain:

- high-resolution small-face images;
- genuine multi-person and false-positive “extra face” cases;
- exact and near duplicates;
- visually similar but semantically useful variations;
- pose/view imbalance;
- outfit/background co-occurrence bias;
- low-quality but coverage-critical samples;
- high-quality but redundant samples.

### 6.2 Human selector benchmark

Create a manually reviewed reference set for:

- hard reject / review / pass;
- duplicate grouping;
- primary face;
- useful vs redundant variants;
- dataset coverage gaps.

This benchmark is used to measure selector behavior, not to train the selector by default.

### 6.3 Actual LoRA outcome benchmark

Because the final goal is LoRA training quality, at least one validation stage must compare actual trained outputs.

Hold constant:

- base model
- training configuration
- caption/tagging policy
- training steps / repeats
- seed set where appropriate
- inference prompts

Compare, at minimum:

- baseline selector output;
- revised selector output;
- carefully curated human reference subset.

Evaluation should include both automated indicators where valid and human review.

#### Required outcome dimensions

- subject/identity fidelity
- prompt adherence
- novel pose/view generalization
- novel environment/background generalization
- outfit/attribute controllability where applicable
- resistance to training-image reproduction / overfitting
- output diversity
- body/face consistency for person/character datasets

The selector is not considered improved merely because detector metrics improve.

## 7. Similarity and diversity

### Keep two separate concepts

#### Near duplicate
Use for almost-the-same images:

- burst frames
- video-adjacent frames
- recompression
- small crop/resize differences

Existing pHash remains useful here.

#### Semantic / visual similarity
Use embeddings to detect images that are not duplicates but may provide overlapping training evidence.

Examples:

- same outfit + same framing + same pose with minor expression change;
- repeated portrait setups;
- compositionally redundant shots.

Embedding similarity must **not** automatically delete samples.

### Human group review

Similarity should produce review groups/clusters, not final deletions.

A future uniqueness value may contribute to recommendation, but only after LoRA-outcome validation.

## 8. Lessons borrowed from FiftyOne

FiftyOne is a workflow reference, not the product architecture.

Useful ideas to borrow:

1. Separate sample-level data from detection/label-level data.
2. Preserve detector outputs and confidence instead of collapsing them immediately into one verdict.
3. Treat filtered/sorted results as a view over persistent dataset state.
4. Provide dedicated similarity/duplicate review.
5. Allow analysis fields to be filtered without coupling them to destructive decisions.
6. Make review state persistent and explicit.

Do not copy:

- generic annotation features unrelated to LoRA selection;
- infrastructure that adds complexity without measurable selector benefit.

## 9. Model-selection policy

The old implicit “prefer small models first” rule is rejected.

Model choice priority:

1. measurable benefit to LoRA dataset selection;
2. accuracy / robustness on our data;
3. relevance to the intended image domain;
4. redistribution/license compatibility;
5. engineering stability;
6. runtime cost;
7. package size.

If a substantially larger model gives a materially better selector result and may legally be redistributed, use and package it.

Lightweight design means avoiding needless cost **without sacrificing selector quality**.

### Packaging rule

If a model is required by the default pipeline and redistribution is permitted, bundle it.

Do not make a required model an online download merely to shrink the package.

## 10. Development phases

### Phase 0 — Evaluation harness and research freeze

**Priority: P0**

Deliverables:

- private benchmark specification;
- selector evaluation schema;
- LoRA A/B validation protocol;
- research table mapping claims -> selector requirements;
- explicit list of metrics that are allowed to hard reject vs only warn/rank.

**Gate:** no new composite recommendation score is frozen before this phase passes.

### Phase 1 — Fix decision architecture

**Priority: P0**

Deliverables:

- `analysis_metrics / review_flags / hard_rejects` separation;
- `PASS / REVIEW / REJECT`;
- primary-face logic;
- persisted face detections and confidence;
- face-box visual inspection;
- migrate existing cache schema safely;
- retain manual override precedence.

**Expected code risk:** medium-high because this touches core analysis semantics and cache compatibility.

### Phase 2 — Review workflow + View model

**Priority: P1**

Deliverables:

- dedicated duplicate-group review;
- explicit scope/filter/sort pipeline;
- preserved Top N / Bottom N workflow with ranking-basis control;
- predictable filter persistence;
- visible current-view description;
- regression tests for view membership/order.

**Expected code risk:** medium-high because current UI behavior is tightly coupled.

### Phase 3 — Dataset-level recommendation

**Priority: P1/P2**

Deliverables:

- coverage representation;
- dataset imbalance analysis;
- redundancy representation;
- dataset-aware marginal sample value;
- recommendation explanation per sample;
- no opaque score without component breakdown.

**Gate:** must beat the baseline in the private LoRA-outcome benchmark before becoming default.

**Expected research risk:** high.

### Phase 4 — Stronger models where evidence supports them

**Priority: conditional**

Potential categories:

- stronger face detection / detector consensus;
- stronger face utility assessment;
- perceptual quality model;
- visual embedding model;
- body/pose/subject representations.

No model is accepted because it is SOTA on an unrelated benchmark. It must improve the LoRA selector benchmark or solve a confirmed failure mode.

## 11. Cost / weight review

### Development complexity

| Area | Relative cost | Main risk |
| --- | --- | --- |
| Decision-state refactor | Medium | cache/status regressions |
| Primary-face + detection QA | Medium | detector edge cases |
| Duplicate-group review UI | Medium | review-state UX |
| View/filter/sort redesign | Medium-High | UI regression |
| Top/Bottom redesign | Low-Medium | state interaction |
| Benchmark/evaluation harness | Medium-High | defining reliable LoRA outcome evaluation |
| Dataset-aware recommendation | High | research validity / overfitting rules to test corpus |
| New model integration | Variable | licensing, conversion, runtime, domain robustness |

Overall v0.3 is a **medium-high engineering effort with high research importance**.

### Runtime / package weight

No fixed MB target is imposed.

The correct optimization targets are:

- run expensive inference once and cache results;
- re-analyze only changed/new images;
- initialize models once and reuse sessions;
- avoid UI operations triggering inference;
- avoid duplicate models that solve the same problem without measurable benefit;
- package required redistributable models.

A heavier package is acceptable if it measurably improves final LoRA dataset quality.

## 12. Non-goals for v0.3

Unless validation shows they are required, do not expand into:

- LoRA training management;
- automatic caption generation;
- scraping / dataset acquisition;
- generic CV annotation;
- full FiftyOne replacement;
- automatic destructive deletion;
- arbitrary “AI score” dashboards unrelated to selection decisions.

---

## 13. Acceptance criteria

v0.3 is not complete until all of the following are true:

1. High-resolution useful small-face images are no longer rejected solely for low face ratio.
2. A false extra face detection does not automatically destroy the sample.
3. Users can inspect face boxes and confidence.
4. Duplicate groups have a dedicated, practical human-review workflow.
5. Top N / Bottom N works on the current view and clearly states its ranking basis.
6. Filters and sorts are predictable and independently understandable.
7. Manual decisions remain authoritative.
8. Recommendation is dataset-aware rather than purely image-local.
9. New scoring/recommendation behavior is validated against LoRA outcomes, not only detector benchmarks.
10. Required models are bundled when redistribution permits.
11. No measurable quality regression is accepted merely to reduce runtime or package size.

---

## 14. Review verdict

**CONDITIONAL PASS**

The direction is correct only if implementation starts with Phase 0 and Phase 1.

The largest risk is prematurely implementing a new composite score before a LoRA-specific validation benchmark exists. The second largest risk is over-expanding into a generic dataset platform.

The recommended sequence is:

```
LoRA outcome definition
-> benchmark
-> fix hard-reject architecture
-> fix human review workflow
-> dataset-level analysis
-> only then freeze model choices and recommendation math
```

This keeps the project centered on its actual job: producing a better LoRA training set.
